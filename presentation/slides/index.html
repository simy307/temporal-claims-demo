01

The Prompt Experiment

A concrete way to see what Temporal can do for your use case.
What I actually typed

My first prompt (verbatim)

chat — untitled idea
> I want to see what temporal workflows can do for me. Create me a project with a UI to track workflow progress and for me to interact with the workflows. Scenario: Claim process for an insurance company. No database, just get state and progress from temporal itself. Use a local temporal instance. Implement any cool ideas you can think of. Make sure there is at lease 1 wait for signal from the UI. Use local storage so the UI persists on refresh.
Read it out loud, typo and all ("at lease 1"). This is intentionally the kind of prompt real engineers write — enthusiastic, directionally correct, structurally thin.
What it became

An excerpt from the full implementation prompt

prompt — Temporal claims demo spec
> Create a working monorepo using:
- Temporal TypeScript SDK
- A local Temporal development server
- NestJS for the backend/API and Temporal worker
- React with TypeScript for the UI
- Docker Compose where useful

Do not use a database. Temporal must be the source of truth for workflow state and progress.

The human-review step should wait indefinitely for an adjuster to approve, deny, or request more information. The UI must clearly show that the workflow is waiting for input and provide controls for sending the appropriate signal.
This is the turning point: the prompt stopped being a wish list and became a set of architectural constraints, Temporal capabilities, UI requirements, and acceptance criteria.
Read it again, like a coding agent has to

What is not said

"…track workflow progress… interact with the workflows… no database… any cool ideas… at lease 1 wait for signal… local storage so it persists…"
  • ? Which failures are transient vs. permanent?
  • ? What must never be lost on a crash?
  • ? Where's the API/worker/UI boundary?
  • ? What does "interact with" mean — signals? updates?
  • ? "Cool ideas" = infinite scope, zero acceptance criteria

None of this makes the prompt bad.

The point isn't "this prompt is bad," it's "this prompt under-specifies exactly the decisions that make or break a durable-execution design." That's the veil.
The move that actually matters

I didn't fix the prompt myself.
I asked AI to fix it.

Why not write the spec by hand?

Because "what should a good Temporal spec contain" is itself a question worth delegating — the model already knows the shape of retries, signals, queries, sagas, especially with a Temporal skill loaded for grounding.

What I asked for

"Would this be good for a coding-agent prompt?" — the answer covered architecture, failure modes, and UI/UX explicitly.

Temporal AI skill: github.com/temporalio/skill-temporal-developer

This is the generalizable trick: use the model to interrogate its own upcoming task — a loaded Temporal skill makes this sharper still. It's cheap, fast, and it front-loads the Temporal-specific vocabulary (retry policy, signal, saga, search attribute) that a vague prompt never would have surfaced.
What came back

The improved prompt condensed

Stack & architecture, named explicitly

Temporal TS SDK · local dev server · NestJS API + worker · React + TS UI · Docker Compose · separate workflow / activity / client / API / UI layers

Durability requirements, named explicitly

retry policies per activity · at least one timer · a child workflow · signals for every human action · queries for state/progress · cancellation handling · failure recovery path

The claim lifecycle, spelled out

9 named stages from submission to payout — not "any cool ideas," a concrete process to map onto primitives

Definition of done

README, unit tests, one integration test that signals a real workflow to completion, build/lint/test must pass before calling it finished

Full text is in the appendix slides at the end if anyone wants to read it verbatim. The point of this slide is the shape, not the word count: every bullet here maps directly to a Temporal primitive we'll see on screen in a few minutes.
The point of this whole talk
Don't be overwhelmed.
You don't need to spell everything out to see what Temporal can do for you.
A sharper prompt makes for a sharper demo — but retries, signals, queries and durability are primitives Temporal gives you either way.
This is the slide to slow down on. The refined prompt made this specific demo cleaner, but the takeaway isn't "write a perfect spec or don't bother." Even the rough first draft would have gotten a working workflow with retries and durability for free — precision just makes the result easier to reason about and demo.
02

What Got Built

An insurance claims console where Temporal — not a database — is the source of truth.
Architecture

Four pieces, one source of truth

React Dashboard

Polls the API and keeps only preferences + recent workflow IDs in localStorage.

NestJS API

REST facade that starts workflows, sends signals, and runs workflow queries.

Temporal Server

Event history, task queues, timers, visibility, and the authoritative claim state.

NestJS Worker

Runs deterministic workflow code and side-effecting activity implementations.

✕ no database, anywhere ✓ Temporal event history is the state ✓ localStorage = prefs + recent ids only
Walk left to right. The UI never talks to Temporal directly — only through the API. The API never runs workflow/activity code — only the worker does. That separation was an explicit ask in the improved prompt, and it's why the demo stays comprehensible.
The business process

Nine stages

1. Submittedworkflow start
2. Validationactivity + retry
3. Coverage checkactivity + retry
4. Damage assessmentheartbeat + cancel
5. Fraud evaluationchild workflow
6. Human reviewsignal · waits forever
7. Decisionsaga: release/reserve
8. Paymentdurable timer + activity
9. Completedworkflow result

Every chip on this rail is a query result, live, from a running Temporal workflow — not a hand-maintained progress bar.

This is the exact stage list from the improved prompt, unchanged. Note stage 6 — "waits forever" — that's the one required signal from the original rough prompt, now precisely specified.

The point isn't the file names — it's that each package has exactly one job: web renders and polls, api translates HTTP to Temporal client calls, worker is the only place workflow and activity code lives. Nothing about a claim's state is duplicated between them. Note activities are one function per file, grouped by domain (claim/, fraud/) — easy to find, easy to unit test in isolation.
Code → observability, for free

Three activity calls. One real execution timeline.

fraud-check.workflow.ts — simplified 
const { checkClaimHistory, checkWatchlists, scoreFraudRisk } =
  proxyActivities<typeof activities>({ ...retryPolicy });

export async function fraudCheckWorkflow(input: ClaimInput) {
  const [history, watchlist] = await Promise.all([
    checkClaimHistory(input),
    checkWatchlists(input),
  ]);
  return await scoreFraudRisk(input.claimId, [...history, ...watchlist]);
}

03

Let's See It Run

Real failures. Real recovery.

DEMO 1 / 6  Submit a claim, watch it run

Dashboard → Submit claim → live redirect Stage timeline updates via polling, no refresh Progress % is computed from stage weights, not hardcoded
Submit the "Happy path" preset claim. Narrate: this whole timeline is one query, getClaimState, polled every 2 seconds. Point out validation → coverage → damage assessment → fraud child workflow completing in a couple seconds each.

DEMO 2 / 6  The workflow waits — forever — for you

Claim parks at "Human adjuster review" Request more info → provide info → back to review Approve → durable settlement timer → paid
This is the required signal from the original prompt. Emphasize: the workflow is genuinely suspended — no polling loop burning compute, no cron job. It resumes the instant the signal arrives, even if that's a week later.

DEMO 3 / 6  Break it a little — watch it heal itself

Arm "transient failure" on damage assessment Activity panel shows attempt 1, 2, 3 — live Same code path, zero extra retry logic written
Point at the "Activity execution & retries" panel — that's Temporal's own attempt counter and last-failure message, not something we built. The retry policy is ~6 lines of config on the proxyActivities call.

DEMO 4 / 6  Break it for real — recover it from the UI

"Break payment (permanent)" → non-retryable ApplicationFailure Claim parks in "blocked on failure" — not crashed, not lost Operator clicks Retry → clears fault → claim completes
This is the failure-handling story: a permanent failure doesn't kill the workflow, it parks it waiting for a human decision (retry or abandon) — same signal mechanism as the business logic, reused for operations.

DEMO 5 / 6  Kill the worker. Mid-claim. On purpose.

"Kill & restart worker" while a claim is blocked worker-…-gen1 dies, worker-…-gen2 comes up Claim resumes exactly where it was — timers included
THE moment of the talk. Nothing in the UI or API restarted — only the worker process. The claim's entire state, history and pending timer survived because none of it ever lived in the worker's memory — it's all Temporal's event history. Let this one breathe; don't rush the narration.

DEMO 6 / 6  Cancel mid-flight — compensations run

Cancel a running claim from the dashboard Reserve released, payment reversed, claimant notified Workflow closes CANCELED — cleanly, not abruptly
If time is short, this is the cut candidate — mention it exists and move to Temporal Web UI / lessons. If time allows, show the non-cancellable compensation scope running even though cancellation was requested.
04

Matching Your Use Case

Pattern match

Signals you have a good Temporal use case

  • ✓ A process that spans minutes, days, or months — not one request/response
  • ✓ Short-lived workflows can still fit — milliseconds or seconds are fine when you need durability, retries, or history
  • ✓ A human has to approve, deny, or provide info at some unknown point
  • ✓ Steps call flaky external systems that need retries with backoff
  • ✓ A crash mid-process must not lose or double-run anything
  • ✓ You need an audit trail of exactly what happened, in order
  • ✓ Multiple steps must be undone together if a later one fails (saga)
Ask the room: "how many of your services already do at least three of these with cron jobs, status columns, and dead-letter queues?" That's usually most of the hands.
The reusable checklist

Durability questions to ask yourself

Ask about failure

What activities can fail transiently? What's permanent? What must be non-retryable?

Ask about waiting

What waits on a human? For how long? What happens if nobody answers?

Ask about state

What must survive a crash? Who is the source of truth — your DB, or the workflow history?

Ask about boundaries

Where does UI end and API begin? Where does API end and worker begin?

Answer these four categories before you design the system, and your Temporal model gets much easier to see.
